# Tongz — design summary

> Tongz — your agent never touches a credential.

AIコーディングエージェント向けの資格情報ブローカー。エージェントが動くコンテナには資格情報を一切置かず、必要な認証だけを外側から付与する。

---

## 1. 脅威モデル

**守る対象**

- コンテナ内のエージェントが、意図しない資格情報にアクセスすること
- 資格情報がコンテナのファイルシステム・環境変数・プロセスメモリに存在すること

**守らない対象(明示的な非目標)**

- ホストの侵害
- ホスト上の他プロセス
- Docker ソケットを持つ人間
- egress 制御(実装は持つが、主張には含めない)

信頼境界は**コンテナの内と外**。ホスト側が侵害された時点でキーチェーンもプロキシのメモリも触れるため、守れるものは残らない。この線引きにより、ARP 偽装・コンテナ間なりすまし・コンテナ名の詐称はいずれも範囲外として扱える。

> トングは掴むための道具であって、鍋つかみではない。

---

## 2. 全体構成

```
ホスト
├── Tongz プロキシ           資格情報を保持(キーチェーン)
│     ├── /install           CA + セットアップスクリプト配布
│     └── MITM + ヘッダー注入
└── コンテナ(エージェント)
      └── HTTPS_PROXY → Tongz、資格情報は持たない
```

- 資格情報はホスト側のキーチェーンにのみ存在
- プロキシは「認証を受け取るための唯一の窓口」
- 経路を回避されても隔離は壊れない。認証が付かないだけ

---

## 3. 主要な設計判断

### 3.1 明示プロキシのみ(透過リダイレクトを採らない)

保証はネットワーク経路ではなく**資格情報の保管場所**で成立している。透過方式はこの保証に何も足さない。

- エージェントは WebFetch 等でネットワーク開放が前提 → 透過方式だと全 443 を掴み、無関係なホストで CA 配布の穴とピンニング破壊が顕在化する
- 明示プロキシなら設定にあるホストだけ復号、残りは CONNECT で素通し。壊れる範囲が設定した分だけに閉じる
- iptables も netns 操作も不要。rootless / CI でも動く

### 3.2 Docker API — 注入はしない、読み取りは任意の強化モード

コンテナの起動フローには割り込まない。生成時の書き換え(env・マウント・netns の注入)を行わない。

- podman / Compose / リモート devcontainer / コンテナでないホストプロセスにも同じプロキシが使える
- 「プロキシを立てて環境変数を向けるだけ」という導入の軽さが得られる

一方、**Docker ソケットの読み取りは傍受ではない**ため、あれば使う。接続元 IP → コンテナ ID → イメージダイジェストが引けるようになり、3.7 の `prompt` / `image` モードの根拠になる。`die` イベント購読によるセッション自動失効も同じ経路。

```yaml
docker:
  enabled: auto     # ソケットがあれば読む(読み取り専用)
  # off             # 読まない。name / any モードのみ
```

- 無くても動く、あれば厳しくなる、という**純粋な加算**として設計する。必須にしない
- 書き込み系 API は一切叩かない。ソケットは `:ro` でマウントすれば足りる
- ただしソケットは読み取りでも強力な情報源(全コンテナの環境変数・マウント構成が見える)。**何のために読むかをドキュメントで明示する**
- どのモードで動作中かは起動時に表示する

### 3.3 ヘッダー注入

**マッチング**はホスト単体では粗すぎるため、ホスト + パス + メソッドで指定する。

```yaml
- match: {host: api.github.com, path: /repos/*/issues, method: [GET, POST]}
  inject: {header: Authorization, format: "Bearer {token}"}
  token: github/repo-scoped
```

- **既存ヘッダーは上書き一択**。追記や尊重にすると、エージェントが自前で用意した資格情報が通ってしまう。「差し込む」ではなく「置き換える」
- 認証方式の大半は宣言的に書けるため、サービス追加のコストはほぼゼロ。署名系(SigV4 等)だけコードが要る
- マッチしないホストは fail-closed で拒否
- 監査ログにはトークンの識別子のみ記録し、値は残さない

### 3.4 GCP の扱い

メタデータサーバー方式は**本物のトークンをコンテナに渡してしまう**ため、タグラインと矛盾する。

- メタデータサーバーは**ダミートークン**を返す(クライアントライブラリが資格情報を見つけられずに落ちるのを防ぐため)
- 実際の認証はプロキシが `Authorization` を本物に差し替えて付与する
- `*.googleapis.com` は API クライアントライブラリからのアクセスであればピンニングされていない。CA を信頼させれば MITM 可能(Chromium 経由の Google 系ドメインは別問題 — 4章参照)
- REST/HTTP API を先行対応。gRPC(Pub/Sub・Firestore・Spanner・Bigtable)は 3.10 の方針で対応する

### 3.5 TLS

- コンテナ → Tongz: **平文 HTTP**。ホスト内で完結し、守るべきものはこの区間を通らない
- Tongz → 外部 API: **TLS 必須**、証明書検証は fail-closed
- 結果として、コンテナ内クライアントの検証が雑(`curl -k` 等)でも外向きの検証は Tongz が保証する
- ホストを跨ぐ構成(リモート devcontainer・CI・チーム共有)に広げる際は内向き TLS が必要になる

### 3.6 セットアップ

CA とセットアップスクリプトを**プロキシ自身が配布**する。配布元が Tongz なので鶏卵問題が起きない。

```
postStartCommand: curl -fsSL http://<gateway>:8080/install | sh
```

- `postCreate` ではなく `postStart` を使う(キャッシュされたコンテナの再起動時にも確実に走る)
- スクリプトが埋める経路: システムトラストストア / `NODE_EXTRA_CA_CERTS` / `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE`(certifi)/ Java cacerts
- devcontainer Feature も併せて提供し、Compose 派にはマウント方式をドキュメントで示す
- インストール失敗時は黙って進まない(CA 無しの TLS エラーは原因が分かりにくい)

### 3.7 接続の認可

`tongz connect` でセッションを確立し、以降の通信を許可する。

- **接続の承認**と**資格情報の承認**を分ける。connect 時点ではどのサービスを使うか未定のため
- 承認の識別子:
  - 恒久ルール → **イメージダイジェスト**(偽装不能、更新が再承認のトリガーになる)
  - セッション → **コンテナ ID**
  - 表示 → name
- モード: `prompt`(最厳格)→ `image` → `name` → `any`。緩いモードはユーザーの明示的な判断
- name モードは開発中の再ビルド用途に有用。脅威モデル上、同一ホスト上のなりすましは元々範囲外なので矛盾しない
- 起動時に**現在のモードを表示**する
- 承認疲れを避けるため、記憶の粒度(コンテナのライフタイム中 / プロファイル単位)を用意する
- セッションは Docker の `die` イベント購読で自動失効させる

### 3.8 パフォーマンス

`.env` を作る動機を生まない速度が要件。

- 証明書生成は **ECDSA P-256**、SNI ごとにキャッシュ、起動時にプリウォーム
- トークン解決を**リクエストパスから外す**。起動時にメモリへ載せ、更新はバックグラウンド(キーチェーンアクセスは ms オーダー、macOS ではプロンプトの可能性もある)
- 非対象トラフィックは CONNECT で splice するだけ

### 3.9 到達制御

- `127.0.0.1` へのバインドは逆効果(コンテナから届かず、ホストの全プロセスから届く)
- ブリッジのゲートウェイ IP にバインドする
- `Proxy-Authorization` にプロキシ利用権のシークレット。サービスの資格情報ではないため、コンテナ内に置いても原則は崩れない
- IP を認証に使わない。認証はシークレット、境界はネットワーク分離、識別は veth

### 3.10 gRPC 対応

gRPC は HTTP/2 上のフレーミング規約であり、**ヘッダー注入に限れば HEADERS フレームを触るだけ**で済む。ボディ(protobuf)はパースしない。

必要なこと:

- **ALPN の整合** — クライアントへ提示する ALPN と上流への接続を揃える。h2 を要求されて h1 を返すと即失敗する
- **HPACK の一貫した処理** — ヘッダーは接続単位の動的テーブルに状態を持つため、1リクエストだけ見て書き換えることができない。接続を通してデコード → 改変 → 再エンコードする
- **擬似ヘッダーの順序** — `:method` `:scheme` `:authority` `:path` は通常ヘッダーより前。崩すとプロトコルエラー
- **ヘッダー名は小文字必須** — gRPC のメタデータは `authorization`。大文字はプロトコルエラー
- **長寿命ストリーム** — 接続確立時のヘッダーは後から更新できない。ストリーミング RPC はトークン期限に注意

対応順序: unary RPC を先行。ストリーミングは後回しでも実用上ほぼ困らない。Pub/Sub と Firestore が動けば「GCP 対応」と言い切れる。

gRPC-Web は HTTP/1.1 上の別物で、こちらは h1 と同じ扱いでよい。

### 3.11 実装言語 — Go

- `golang.org/x/net/http2` と `hpack` が使え、`ReverseProxy` も h2 を扱える。gRPC 対応がフルスクラッチにならない
- `crypto/tls` の `GetCertificate` フックで SNI ごとの動的なリーフ証明書発行が数十行で書ける。ECDSA 生成も標準ライブラリ
- 単一バイナリのクロスコンパイル。`/install` エンドポイントから全プラットフォーム分を配れる
- Go 製 MITM プロキシの参考実装が豊富(martian、goproxy 等)

Rust は性能面で上だが、ボトルネックは TLS ハンドシェイクとネットワークであり言語差が出る場所ではない。キーチェーン連携は `github.com/99designs/keyring` 等で吸収できるが、macOS のアクセス制御をバイナリに紐付ける部分は cgo か外部コマンド呼び出しになる。

## 4. 残る課題

- **マウントされたリポジトリ内の資格情報**(`.env`、`~/.npmrc`、git remote の埋め込みトークン)は防ぎきれない。検出して警告するか、範囲外と明示するかの判断が必要
- **MITM できないクライアント**。真のピンニングより、独自トラストストアのほうが実際には多い。fail-closed で落とし、既知の非対応は `passthrough: true`(復号せず素通し、認証注入も不可)で逃がす
  - **Chromium 系**(Playwright / Puppeteer) — Google 系ドメインに組み込みピン。独自の NSS ストアも参照する。エージェントのブラウザ操作は今後増える領域なので早めに検証したい
  - **Rust + rustls(`webpki-roots`)** — ルート証明書がバイナリに焼き込まれ、環境変数で上書きできない。`rustls-native-certs` ビルドなら問題ないが、利用者側から判別できない
  - 自前で `RootCAs` を固定している Go 製 CLI(社内ツールに多い)
  - Python(certifi)/ Node / Java / Deno は独自ストアだが、3.6 のインストールスクリプトで埋まる
- **HTTP/2 と WebSocket** のアップグレードを踏むため、ヘッダー書き換えを HTTP/1.1 前提で実装しない
- **名前の確保**: npm / crates.io / PyPI / Homebrew / GitHub org / ドメイン

## 5. この設計に至った経緯(要約)

削ることで主張が強くなった、という流れ。

1. egress 制御を主張から降ろした(コンテナなら自前で組める = 差別化にならない)
2. 透過方式をやめた(保証は資格情報の保管場所で成立しており、経路の強制は不要)
3. 起動への関与をやめた(注入が不要になり、対応環境が広がった)
4. 脅威モデルをコンテナ境界に限定した(細かい偽装対策の判断が一括で解決した)
